llm_services — a multi-tenant gateway between many customers and many model providers

Multi-tenant inference gateway · provider abstraction · streaming execution

Platform Engineering Problem — Many customers, each with their own credentials, models and limits, need to reach many model providers through one API that never lets one tenant spend, read or break another tenant's anything

A client sends a chat, embedding or rerank request naming only a tenant and a deployment key — never a provider, a model, an endpoint or a key. Everything that decides what actually happens is resolved server-side: who the caller is, whether this tenant may use this deployment, which entitlement grants it, which provider and model that entitlement points at, which credential sits behind it in the vault, and whether there is capacity left against a ceiling that is shared by every replica. Only then is a provider dialled, behind one internal contract that five vendor adapters implement identically. The client API therefore stays still while provider choices move underneath it.

How to read the Run Inference lane

  1. Steps 1-5 — Security. Who are you, and are you allowed?
  2. Steps 6-9 — Logistics. What should run, and is there room to run it?
  3. Steps 10-11 — Execution. Get the key, call the AI.
  4. Steps 12-13 — Cleanup. Return the answer, record the cost, free the space.

Who owns what

  • Tenant — one organisation using the platform; the isolation boundary. It owns its Deployments.
  • User — global, not owned by a Tenant. One User can belong to several Tenants, one membership row each.
  • Deployment — one saved AI configuration belonging to one Tenant, e.g. gpt4-prod. It names a provider, a model and an endpoint.
  • Entitlement — grants one User one Deployment. Belonging to a Tenant does not grant its Deployments — that is why step 5 checks membership and entitlement separately.
